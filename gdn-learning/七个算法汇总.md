# GDN / MTP 的 n+1 份状态问题：7 个算法汇总

写于 2026-10-29。

**结构**：先用「读写流水账」讲清楚一轮 decode 读了什么写了什么、为什么必须这样 → 再解释「链和树」→ 再给「七个算法的思路概览」→ 最后每个算法按同样的 7 项展开：论文地址 / 实现思路 / 解决什么问题 / 开源代码仓 / 实现情况 / 相关 PR 和 issue / 在 Ascend 上怎么做。

## 先用三句话交代背景

1. **GDN 层**（Qwen3.5/3.6/3.8 这类模型里大量使用的线性注意力层）不像普通 Transformer 那样为每个 token 存一份 K/V，而是维护**一个固定大小的小矩阵当"状态"**，每读一个 token 就往这个矩阵上改一笔。整个历史都压在这一个矩阵里。
2. **投机解码**（MTP 是其中一种）一次要往前猜 n 个 token，让模型**一次性并行验证**这 n+1 个位置（1 个已确认 + n 个候选）。但状态是"改一笔、传下一笔"的顺序结构，验证完才知道哪几个猜对了，于是现在所有框架的做法是：**每验证一个候选位置，就完整复制一份状态存着**。等于要 **n+1 份状态**。
3. 一份状态就不小（35B 模型、256 并发，一份约 7.7 GB），乘 4 倍就是 30 GB。**这 7 个算法就是来解决这事的。**

> 后面会反复出现两个词：**链**（MTP 这样只猜一条路）和**树**（EAGLE 这样每个位置猜多个分支）。
> 区别、示意图、以及为什么它决定了方案难度，见下面「链和树是什么」一节。

## 一轮 decode 到底读了什么、写了什么

要看懂这 7 个算法在省什么，先把"一次前向的读写流水账"摊开。以下都是**现状**（未做任何优化），也就是 vLLM / SGLang 默认在做的事。

### 先算清楚"一份状态"有多大

GDN 层给每个 value head 维护一个小矩阵，形状 `d_k × d_v`（一般 128×128）。以 Qwen3.5-35B 这类配置（30 个 GDN 层、32 个 value head、FP32）为例：

```
一层一个序列：32 heads × 128 × 128 × 4 B = 2 MiB
30 层一个序列：                          = 60 MiB
256 并发：                              = 15 GiB     ← 这还只是"一份"
```

后面所有读写，都是围着这 60 MiB 转。

### 阶段 A：Prefill（整段 prompt，只做一次）

| 动作 | 读 | 写 |
|---|---|---|
| 逐层算 | 模型权重（全 batch 共享） | — |
| 存 KV | — | 普通注意力层的 KV，随上下文长度线性增长 |
| 存状态 | — | **1 份** GDN 状态（60 MiB/序列） |
| 存卷积状态 | — | 1 份（很短） |

到此为止是健康的：一个序列一份状态。

### 阶段 B：每一轮 decode（被放大的就是这里）

拿 MTP、K=3（猜 3 个 token，验证 4 个位置）举例。

```
B1. MTP 草稿
    跑 K 次小的草稿层（通常就是普通注意力层 + MoE，不碰 GDN 状态）
    读：上一轮目标模型的 hidden state、草稿自己的 KV
    写：K 条草稿 KV（几 KiB 级，很小）

B2. 目标模型一次前向，验证 4 个位置
    对每个 GDN 层（共 30 层，逐层）：
      读：模型权重
      读：1 份已确认的状态（上一轮活下来的那份）
      算：4 个位置顺着推（位置 0→1→2→3，必须串行）
      写：4 份状态 → 落到 4 个不同的状态槽
    对普通注意力层：
      读 KV 前缀；写 4 条新 KV（指针追加，很便宜）
    对卷积状态：
      写成"一份加宽的表"（长度 = conv_kernel-1 + K），靠记偏移量回退
      → 不乘 4 份

B3. 采样
    读 4 个位置的 logits，算出接受长度 a（0~3）

B4. 收尾
    把"第 a 个槽"指定为下一轮的基准状态 → 只改索引，不拷贝
    KV 截断到 a+1 条；没被接受的 3 个槽标记为可复用
```

**关键就在 B2 那一行"写 4 份"**：验证是 4 个位置一起算的，**算完才知道接受哪几个**。所以在知道答案之前，只能把 4 个位置的状态全写下来。而且这不是"每步写 4 份"，是"**每步 30 层 × 4 份 = 120 份**"。

### 流量摊开看

一个序列、一轮 decode（K=3，FP32 状态）：

| 对象 | 读 | 写 | 说明 |
|---|---|---|---|
| 模型权重 | 1 次/层 | — | 全 batch 共享，**投机解码省的就是这笔**：一次读权重算 4 个 token |
| KV（前缀） | 随上下文 | 4 条 | 追加式，几 KiB，可忽略 |
| 卷积状态 | 1 份（很短） | 1 份加宽表 | **不乘 4** |
| **GDN 状态** | **60 MiB** | **4 × 60 = 240 MiB** | **只有 1/4 是最终留下的** |
| 合计（状态部分） | 60 MiB | 240 MiB | 基线是 60+60 = 120 MiB |

- **写放大 = K+1 = 4 倍**，其中 **3/4 是白写的**（写完立刻丢弃）。
- 并发 256 时：**读 15 GiB、写 60 GiB，每步**。不是算不动，是搬不动。
- SGLang 源码里一句注释很能说明比例：这块"每个候选位置一份状态"的暂存，体积是卷积状态的 **约 46 倍**。

**一个不对称**：卷积状态因为有"加宽表 + 偏移回退"这个技巧，**不用乘 n+1**；只有那个 `d_k × d_v` 的矩阵状态必须乘。所以所有方案都在矩阵状态上做文章。

### 那为什么不能"在 SRAM 里挑一个留下"

会有人问：既然 4 份状态在 kernel 内部本来就在片上（SRAM / 寄存器），为什么不在片上选完再写一次？

**答案：写在 HBM（分页状态池），而且不能在片上选。** 两个独立原因：

**原因一：时间对不上（根本原因）**

| 事件 | 发生在哪 |
|---|---|
| 写 4 份状态 | **第 1 个 GDN 层**的 kernel 里 |
| 知道该留哪一份 | **30 个 GDN 层全部跑完之后**，还要再过采样 |

中间隔着 29 层前向 + 采样，而 **SRAM 不跨 kernel、不跨层存活**——kernel 一退出，片上内容就没了。等你知道答案时，第 1 层那份 SRAM 早被后面的层覆盖了。

**原因二：容量也放不下**

```
一个 head 的一份状态：128 × 128 × 4 B = 64 KiB
4 份：                                 256 KiB
一层 32 个 head 的 4 份：              8 MiB     ← 只算一层、只算一个序列
30 层：                                240 MiB
```

对照片上容量：H100 一个 SM 的共享内存 228 KiB、**全芯片约 30 MB**；昇腾一个 AI Core 的 UB 约 192 KiB、**整芯片也是 MB 级**。**一层一个序列的 4 份（8 MiB）就吃掉全芯片 SRAM 的一大块**，而我们要服务 batch=256。

> 顺带否掉另一个想法：**"先写进临时 scratch，挑完再拷进正式槽"**——没用，字节数一点没少，只是换个地方写。要省必须**少写数据**，不是**换个地方写**。

### 为什么验收必须等所有层（"逐层验收"为什么不行）

两个方向要分开看：

| 方向 | 性质 | 后果 |
|---|---|---|
| **深度（层）** | 串行、只走一遍、不回头 | 某一时刻只碰一层的 state |
| **时间（token 位置）** | **所有层共享同一个坐标** | 接受 `a` 个 token ⇒ **30 层全部前进 `a` 步** |

- **在"最后一层算 logits 的那一刻"，确实只读 `S₃₀`**（加上 `h₂₉`）。`S₁…S₂₉` 是在更早的时刻被各自的层读掉的。这一点没错。
- 但 `a` 是**全局**的：接受了 3 个 token，30 层**全部**要往前推 3 步。只要有一层对不上，`h₁` 就错，一路错到 `h₃₀`。
- 所以下一轮开始时，每层都要从"自己那 4 份候选里的第 `a` 份"继续——**这就是 30 层都要各自存候选的原因**。

**为什么不能逐层验收**：验收要的是"下一个 token 的概率分布"，它只在**最后一层 + lm_head 之后**才存在。中间层只有输出激活（hidden state）和状态摘要，没有 token 分布。用中间层判，等于换了一个模型（那就是 early-exit，不是投机解码），**输出分布会变**，直接破坏投机解码"无损"的前提。

### 一句话：谁在等谁

> **验收不需要 state，是 state 在等验收。**
> 现状的问题是"等"的这段时间里，每层都霸占着 4 份完整状态（30 层 × 4 = 240 MiB）。优化的方向就是：等的时候只留 1 KiB 的"改动记录"，等完了再重算那一份。

## 链和树是什么

两个词说的是**草稿（猜出来的候选 token）摆成什么形状**。

### 链（chain）：只猜一条路

MTP 就是链，一个一个往后猜：

```
已确认: "今天"            ← 位置 0（不是猜的）
         │
         ├─ 猜1: "天气"    ← 位置 1
         │      │
         │      └─ 猜2: "很好"    ← 位置 2
         │             │
         │             └─ 猜3: "。"  ← 位置 3
```

- 4 个位置，**每个位置只有一个候选**；
- 第 2 个候选是把第 1 个候选**当成真的**继续往后猜的；
- **前面错一个，后面全废**。
- 验收：从位置 1 开始逐个比，遇到第一个不接受的停住 —— 拿到的是"一个前缀"。

### 树（tree）：每个位置猜多个分支

EAGLE、Medusa 这类会做树：

```
已确认: "今天"
         │
    ┌────┴────┐
  "天气"     "晚上"          ← 位置 1 猜了 2 个
    │          │
 ┌──┴──┐   ┌──┴──┐
"很好" "不错" "吃" "去"      ← 位置 2 各猜 2 个
```

- 节点 7 个，**位置还是 3 层**；
- 路径有多条：`天气→很好`、`天气→不错`、`晚上→吃`、`晚上→去`；
- **好处**："天气"错了但"晚上"对了还能救回来 —— 一个位置猜错不一定全废，所以平均接受长度更高（EAGLE-2 报 4–5.5 个 token/轮，链一般 3 出头）；
- 验收：在整棵树上**选一条从根到某个节点的路径**，其余分支全丢。

### 三个关键差别

| | 链 | 树 |
|---|---|---|
| 每层候选数 | 1 | 多个（2–8） |
| 总节点数 | K 个（K=3 → 4 个位置） | 可到几十（如 39 个节点） |
| 每个节点"该看见谁" | 前面所有节点 | **只有自己的祖先**，兄弟/堂兄弟都看不见 |
| 验收 | 前缀式（数到哪停） | 在树上选一条路径 |
| 状态份数 | K+1 | **N+1（N = 节点总数）** |

### 为什么这两个字在这个题目里这么要紧

**只有一点：树上那套"每个节点只看得见自己祖先"的规则，叫"非因果掩码"。**

- 链的规则是"每个位置看得见前面所有位置"——就是普通的因果掩码，**所有现有 kernel 都天生支持**，也能被整图捕获；
- 树的规则是**任意形状的父子关系**，kernel 里得按拓扑结构取数据，而且**每个节点的状态互不相同、谁也不能代表谁**，所以：
  1. **状态必须 N+1 份**（不能共用）；
  2. kernel 不能按"顺序数组"处理，得按"树结构"处理；
  3. 一旦这个掩码的形状是运行时才定的，**整图捕获就废了**——这正是 TreeWY 在 GPU 上做树反而变慢的原因。

> **链 = 一条线，天然顺着现有实现；树 = 一张网，接受率更高，但状态更多、kernel 更难写、图更难捕获。**
> MTP 是链，EAGLE 是树。

## 七个算法的思路概览

先记住所有正解共用的那一个观察：

```
"改成什么" = 一份完整状态      128 × 128 = 16384 个数 = 64 KiB
"改了哪些" = k、v、β、g        128+128+2 = 258 个数 ≈ 1 KiB
```

**差 64 倍。** 而给一个起点状态 + 沿途每一步"改了哪些"，就能把任意一步的状态重算出来。所以 4 份 64 KiB 的状态（一层 256 KiB），可以换成 **4 份 1 KiB 的记录**（一层 4 KiB）。

7 个算法里，**前 4 个是直接解决"4 份"的**，后 3 个是"每份多大 / 写得多不多"的补丁：

### 正解 1：ReplaySSM —— 存原始输入，靠挪指针回退

- 状态 = **一个检查点 + 最近 16 步的输入记录**；每步只追加，**不碰大矩阵**，攒满 16 条才合并一次。
- 猜错了 → **把记录指针往回挪一格**，零拷贝。
- 验证时直接算输出，**不生成任何中间状态**。
- 限制：只支持链。**7 个里唯一进生产、且有官方代码的。**

### 正解 2：TreeWY —— 树上一次解方程

- 树的分支没法共用快照，所以干脆不存状态。
- 把每个节点的输出写成"起点状态 + 祖先改动量的加权和"，代回去变成**一个下三角线性方程组**，**解一次就得到所有节点的输出**。
- 只存每个节点一个长度 128 的向量（比 128×128 小 128 倍）。
- 限制：内存问题解决了，但**树版本实测更慢**（非因果掩码导致整图捕获失败）；无公开代码。

### 正解 3：Bole —— 同样的方程，换成 4 次矩阵乘

- 和 TreeWY 是**同一个方程**，但注意到树深度只有 3–4，所以"解方程"可以展开成 `I − G + G² − G³`，**4 次矩阵乘就精确结束**。
- 把"不友好的三角求解"变成"最友好的矩阵乘"，还能按输出列切块并行。
- 只留 1 份状态 + 每个节点三个小因子；接受后用**一次矩阵乘**拼出新状态。
- 限制：无公开代码。**但对 Ascend 最有参考价值**（Cube 单元就吃矩阵乘）。

### 正解 4：SpecLA —— 按候选形状分三种路

- 短链：状态留在片上改，一次都不写回显存。
- 树：把"只能看祖先"的掩码塞进方程，一次解出来（与上面同一套）。
- **多链：链内串行、链间并行**（实测最快，比"逐条重放"快 1.8–7.1×）。
- 额外一招：验证时本来就算出了那些改动因子，缓存起来；采样后只取被接受那条，**把状态更新推到下一次验证里做**，省一次独立步骤。
- 限制：纯 GDN、无 MTP、无代码；它自己的"并行树"实测比串行还慢。

### 补丁 1：DeltaLog —— 减写回次数

就算份数降到 1 份，每步把 64 KiB 写回去仍然很贵。它把状态拆成"稠密底 + 最近更新日志"，攒 8 步才写回一次，**写流量降 7.8×**。（只做单 token 解码，不含投机窗口。）

### 补丁 2：DAMP —— 减每份大小

把状态压成混合精度：少数"高风险"通道存 FP16，其余 INT8，**存储降 69%**。（均匀压到 BF16 会掉 5.75 分、压到 INT8 直接崩，所以必须混合。）

### 补丁 3：DASC —— 另一个战场

它解决的不是投机解码，是**前缀缓存**里的状态检查点太大，和投机解码抢同一块显存。

### 收束：前 4 个是"别存结果、存原料、事后重算"，后 3 个是"把原料/结果本身压小"

## 一句话总览

| 算法 | 怎么省 | 能省到 | 有代码吗 | 在 Ascend 上 |
|---|---|---|---|---|
| **ReplaySSM** | 状态 = 检查点 + 最近几步的输入记录 | n+1 份 → 1 份 | ✅ 有官方 | **最容易，已有 Ascend PR** |
| **TreeWY** | 把整棵候选树的输出一次性解方程算出来 | n+1 份 → 1 份 | ❌ | 链可以，树不建议 |
| **Bole** | 同上，但用 3–4 次矩阵乘代替解方程 | n+1 份 → 1 份 | ❌ | 矩阵乘思路最适合 Ascend |
| **SpecLA** | 按链/树/多链分三种路走 | n+1 份 → 1 份 | ❌ | 多链并行那条最合适 |
| **DeltaLog** | 不每步写回状态，攒着每 8 步写一次 | 不减份数，减写入量 | ❌ | 收益在 Ascend 上更大 |
| **DAMP** | 状态用混合精度存 | 不减份数，减每份大小 69% | ❌ | 能省 HBM = 能上更多并发 |
| **DASC** | 只给"记得久"的部分存检查点 | 不减份数，压缩检查点 | ❌ | 布局不友好，需改造 |

# 1. ReplaySSM

**论文地址**：<https://arxiv.org/abs/2610.13778>（arXiv:2610.13778，2026-10-09）
作者：Ze-Wei Liou、Harris Nover、Amey Naik、Andrii Skliar、Igor Shovkun、Ido Shahaf、**Tri Dao**（普林斯顿大学 + NVIDIA）

**解决什么问题**
两个问题，同一个根因：
- 每生成一个 token，都要把整个状态矩阵读进来、改一笔、再写回去。写回去的字节数远远超过这个 token 真正带来的信息量，纯属搬运。
- 投机解码要 n+1 份状态（就是开头说的那个问题），内存压不住并发。

**实现思路**
把"状态"换一种存法：**不是一个矩阵，而是"一个检查点 + 最近几步的原始输入记录"**。

- 每步只把 `(α, k, v)` 这几个小向量追加到记录里，**不动那个大矩阵**；
- 记录攒满（默认 16 条）才真正合并回检查点一次；
- 猜错了要回滚？**把记录的读指针往回挪一格就行**，一个字节都不用拷；
- 验证多个候选时，用等价公式直接算输出（`o = S·Q·D + V*(W⊙(KᵀQ))`），**全程不生成任何中间状态**；
- 还有一个副产品：检查点可以存两份，一份 FP32 只负责往下递推，一份低精度只负责算输出。低精度的舍入误差永远不会回流进递推。

**有没有开源代码仓**
有，官方：<https://github.com/Johnny-Liou/ReplaySSM>（Apache-2.0，是 vLLM 的 fork，含 Mamba2 和 GDN 两套实现）

**实现情况**

| 框架 | 状态 |
|---|---|

**查 vllm / ascend 的相关 PR 和 issue**

- vLLM：RFC [#47572](https://github.com/vllm-project/vllm/issues/47572)（open）。上游把这条路线叫 **RecoverSSM**，开关 `--use-replayssm`。GDN 的接线仍在 open：[#61309](https://github.com/vllm-project/vllm/pull/61309)（Qwen3.5/3-Next）、[#58863](https://github.com/vllm-project/vllm/pull/58863)（Qwen4Exp）；配套还有 [#62625](https://github.com/vllm-project/vllm/pull/62625)（恢复记录别放 Mamba page）、[#61017](https://github.com/vllm-project/vllm/pull/61017)（多 KV group 一次提交）、[#59983](https://github.com/vllm-project/vllm/pull/59983)（流水并行）。
- vLLM 里"n+1"在代码中的出处：`vllm/v1/kv_cache_interface.py`
  ```python
  max_memory_usage_bytes = page_size_bytes * (1 + num_speculative_blocks)   # num_speculative_blocks = K
  ```
  开 RecoverSSM 时 `num_speculative_blocks = 0`，这一行就变成 ×1。
- vllm-ascend：**PR [#18765](https://github.com/vllm-project/vllm-ascend/pull/18765)**（open）就是干这个的，实测 *48 value heads, K=V=128, MTP3 → 状态+记录约 3.188 MiB，而 4 份快照要 12 MiB*；**RFC [#19987](https://github.com/vllm-project/vllm-ascend/issues/19987)**（2026-10-27 开）要把它推进到新的 ModelRunner V2。

**在 Ascend 上怎么实现、有什么问题**

思路：这是 7 个里最容易落 Ascend 的一个。只需要两个固定形状的 kernel——"追加"和"合并"，正好可以套昇腾的 ACL Graph 双图（一张图管追加、一张管合并）。
- 关键算子只有两个：`KᵀQ` 这种小矩阵乘（走 Cube 单元），以及沿序列长度做一次累积衰减（走 Vector 单元，FP32）。
- 解那个小方程组（长度 ≤16）建议用 3–4 次固定大小的矩阵乘，而不是三角求解。

问题：
1. **MTP 长度是编译期常量**。vllm-ascend 的 GDN 算子里 `MAX_MTP` 写死在 tiling 里（[#11236](https://github.com/vllm-project/vllm-ascend/pull/11236) 刚从 8 改成 16）。改宽验证窗口必须**同步改 host 侧的 UB 显存核算**，否则会 UB 溢出、静默算错（这个坑 #11236 的评审已经踩过一次）。
2. **#18765 的适用范围很窄**：A2/A3、单卡、老的 ModelRunner V1、关 prefix caching、只支持 bf16 模型 + FP32 状态。
3. **游标是 host 侧逻辑**（`write_pos = steps % L`），跨图捕获时容易出 bug，上游为此有一串 bugfix。
4. **prefix caching 不兼容**（要开就得上 V2 runner）。

# 2. TreeWY

**论文地址**：<https://arxiv.org/abs/2608.20961>（arXiv:2608.20961，v2 2026-10-22）
作者：Sneha Murthy Ghantasala（Thomson Reuters），单作者

**解决什么问题**
只解决"树"的那一半：快照方案下，一棵候选树有 N 个节点就要 N+1 份状态，而且**分支之间不能共用**（兄弟节点各自写了不同的东西，谁也不能代表谁）。于是"把树开宽一点、接受率更高"这件事在内存上直接做不了。这篇的目标是**把快照彻底删掉**。

**实现思路**
思路很直接：**候选节点的输出，不一定要一步一步推着算**。

- 把树上所有候选节点按"祖先排在前面"的顺序编号；
- 对每个节点，它的输出 = "起点状态的贡献" + "它所有祖先（含自己）写入量的加权和"。权重只是路径上衰减系数的乘积；
- 但"写入量"本身又依赖于父节点的状态，代回去之后，就变成一个**下三角的线性方程组**，解一次就得到**所有节点**的输出；
- 猜对了哪个节点，就只把那个节点的祖先链重新算一遍得到它的状态，**其他节点的状态一个都不用存**；
- 存的东西从"每个节点一个 128×128 矩阵"变成"每个节点一个长度 128 的向量"，**小 128 倍**。

（这个"解一次方程组"的做法并不是它发明的，是 DeltaNet 里已有的技巧；它做的事是把这个技巧从"一段连续序列"推广到"一棵树"。）

**有没有开源代码仓**
**没有。** 作者明说实现是 vLLM 的私有 fork，"not yet upstreamed as of this writing"。GitHub 上搜 TreeWY 只有一个同名的空白个人主页仓库，不是这个工作。

**实现情况**

| 框架 | 状态 |
|---|---|
| **vLLM** | 私有 fork，暴露成两个配置项：`mamba_state_commit="reconstruct"`、`draft_tree_widths`。作者分支 `sneha5gsm:vllm:treewy-gdn-spec-decode`（commit `b073ed6`）。有 RFC [#54080](https://github.com/vllm-project/vllm/pull/54080)（open），但**没有 PR** |
| SGLang | 无 |
| vllm-ascend | 无 |

**查 vllm / ascend 的相关 PR 和 issue**

- vLLM RFC [#54080](https://github.com/vllm-project/vllm/pull/54080)：这是全网**唯一给出 n+1 内存硬数字**的地方——Qwen3.5-397B 每层每序列状态 **90 MiB**，深度 3 的链共 **360 MiB**，`[2,2,2]` 的树约 **1.2 GiB**。
- 同一个 RFC 也自己承认了失败原因：
  > "*Draft trees are not a throughput win yet … **throughput falls at every width**. The cause is **CUDA graph capture**.*"
  因为树的掩码是"非因果"的，整个模型无法用 CUDA Graph 整图捕获，就得退化成一段段单独跑，连 GDN 层都被踢出图，**代价比掩码本身大得多**。
- vllm-ascend 侧没有相关 PR/issue，但有一个 **RFC [#18797](https://github.com/vllm-project/vllm-ascend/issues/18797)「Tree Speculative Decoding」**，它提的 GDN 方案更朴素：**每条链各自维护自己的状态，只保留被接受的那条链**（接受后重算），不是 Bole/TreeWY 那种闭式解。

**在 Ascend 上怎么实现、有什么问题**

- **链可以照做**：链的掩码还是因果的，能进图，这是安全的部分。
- **树不建议第一版做**：原因和它在 GPU 上失败的原因一模一样——非因果掩码无法整图捕获。Ascend 的 ACL Graph 对动态形状/动态掩码只会更敏感，一旦掉图，省下的内存换不回掉下去的速度。
- 可以借的一点是它的**求解方式可以换成矩阵乘**（见下一个 Bole），这样至少把"形状"固定住。

# 3. Bole

**论文地址**：<https://arxiv.org/abs/2608.01651>（arXiv:2608.01651，2026-08-03）
作者：Li Wang、Yi Su、Xiabao Wu、Chiran You、Yongchao Liu、Zhan Qiu、…、Chengying Huan（南京大学 + 蚂蚁集团 + 上海交大 + 北大）
注意：PDF 页眉写着 **"HPCA 2027 Submission #814 / Confidential Draft"**，是投稿中的非正式版本，许可协议 CC BY-NC-SA（禁商用）。

**解决什么问题**
和 TreeWY 同一个问题，但从"算子 + 运行时"两头一起做，并把代价量化得很清楚（Qwen3.5 系列，A100/GB10 实测）：

- **分支要一个个跑**：树从 8 个节点加到 64 个，线性层的耗时占整个前向的比例从 **4% 涨到 27%**；
- **每个节点一份完整状态**：Qwen3.5-122B 上，8 个 32 节点的请求就要 **36 GiB** 快照，再大一点 **72 GiB**；而它自己的方案**不到 1 GiB**；
- **不是加越多 token 越划算**：超过一个和硬件相关的阈值后，矩阵乘从"读权重为主"变成"算力为主"，延迟开始随 token 数线性涨。实测拐点 **A100 约 128 行、GB10 约 256 行**。

**实现思路**
三件事：

1. **和 TreeWY 是同一个方程**，但**解法不同**——这是最关键的一点。它注意到：那个下三角矩阵是"按深度分层"的，深度只有 3–4（MTP 就那么深），所以 `(I+G)⁻¹ = I − G + G² − G³ + …`，展开到第 4 项就精确结束了。
   **于是"解一个三角方程组"变成了 3–4 次普通的矩阵乘。**
2. **按输出的列切块并行**：那个 `N×N` 的系数矩阵和输出的每一列都无关，所以把输出的 128 列切成几块，每块一个计算核，系数只算一次大家共用；中间结果全部留在片上，不落显存。
3. **状态只留一份**：验证时只保留"已确认的那一份状态"，每个候选节点只存 `(路径衰减, key, 写入量)` 三个小东西。接受之后，只把被接受路径拼起来做**一次矩阵乘**，得到新状态；被拒的分支不占任何内存，也不需要回滚。
4. 另外还有个"按硬件实测的验证预算"：一次性测出这台机器一次最多高效验证多少 token，运行时按候选的累积概率跨请求分配。

**效果**：树验证快 **3.4–7.7×**，瞬时状态内存降 **82–99×**，离线解码吞吐最高是自回归的 **4.72×**。

**有没有开源代码仓**
**没有。** 没有仓库、没有分支、没有作者的 PR。论文声称"集成进了 SGLang"，但**不可证实**：论文里唯一的 SGLang 链接是它的基线版本 `release/v0.5.12`，所谓"约 6.2 kLoC 的集成代码"是私有的。
唯一公开的实现是一个**第三方** PR：[sglang#46702](https://github.com/sgl-project/sglang/pull/46702)（open，2026-10-27），但它自己写明 "**Not supported yet … EAGLE tree verify**"，也就是说**只做了链，树的卖点没实现**。

**实现情况**

| 框架 | 状态 |
|---|---|
| SGLang | 作者声称集成，**无公开代码可验证** |
| vLLM | 无 |
| vllm-ascend | 无 |

**查 vllm / ascend 的相关 PR 和 issue**

- 搜 "Bole"：vLLM、SGLang、vllm-ascend 都**没有**对应的 PR/issue。
- 但它揭示的两个问题在上游是真实存在的、并且有人在解：树的"非因果掩码掉图"（vLLM RFC #54080）、"验证宽度有硬件阈值"（Bole 自己的贡献，上游还没有对应实现）。
- 它是把树做成"插件"的动机来源之一：vLLM [#62962](https://github.com/vllm-project/vllm/pull/62962) 加了一个 `LinearAttnVerifyExtension`（让线性注意力层把待验证的行以零拷贝视图交给外部的验证器）+ 投机方法注册表，[#62963](https://github.com/vllm-project/vllm/pull/62963) 加了 MRV2 的 hooks；vllm-ascend 对应镜像了 [#19603](https://github.com/vllm-project/vllm-ascend/pull/19603)、[#19604](https://github.com/vllm-project/vllm-ascend/pull/19604)。

**在 Ascend 上怎么实现、有什么问题**

**这篇是 7 个里对 Ascend 最有参考价值的**，就因为它把"解方程"换成了"3–4 次矩阵乘"：
- 昇腾的 Cube 单元最擅长的就是矩阵乘；而 CANN 里没有现成的"三角方程组求解"算子，硬写会变成串行的标量循环。
- 矩阵乘的形状是固定的（`N×N` 乘 `N×128`，N 由最大树宽决定），**输入只有数值在变、形状不变** → 这是能不能进 ACL Graph 的关键条件（**这一点目前没有任何公开验证，必须自己先做 microbench**）。
- 按输出列切块、系数算一次共用，这个思路可以直接照搬到昇腾的 UB 预算里。

问题：
1. **没有参考代码**，得自己从论文的公式实现，并且要自己证明数值正确。
2. **Neumann 展开的浮点误差没有任何公开数据**（论文只证明"代数上精确"）。bf16 下连乘 4 次，误差多大是未知的，必须自己测。
3. 需要自己做 profiler 标定"昇腾上一次最多高效验证多少 token"（不同型号 UB/Cube 配比不同，拐点会完全不一样）。

# 4. SpecLA

**论文地址**：<https://arxiv.org/abs/2607.16673>（arXiv:2607.16673，2026-07-18）
作者：南京大学（新型软件技术国家重点实验室）+ 阿里巴巴

**解决什么问题**
它把"为什么投机解码在 GDN 上做不了"讲得最清楚，指出两种照抄的做法都不行：
- **拿单步解码 kernel 一个候选一个候选地跑**：那"每 token 读一遍写一遍状态"这件事一点没省，投机解码本来要摊销的就是这个；树还要为每个分支准备不同的中间状态，更糟。
- **拿预填充 kernel 把候选当一小段序列跑**：投机窗口太短（3–8 个 token），预填充那套准备工作（布局转换、分块、求解、同步）根本摊不掉；而且普通预填充是"每个位置能看见前面所有位置"，而树要求"每个候选只能看见自己的祖先路径"，依赖关系对不上。

**实现思路**
三层，核心是第一层的"按候选形状分三路走"：

1. **短链**：状态块一直留在片上（不落显存），沿着 token 顺序改，一次都不写回。
2. **树**：把"只能看见祖先"的掩码塞进那个线性方程组里，一次解出来（和 TreeWY/Bole 同一套东西）。
3. **多链**：链内还是串行跑，但**互不依赖的链之间并行**。它不用准备整棵树的那套东西，实现轻，实测比"从根到叶逐个重放"快 **1.80–7.11×**——**这是它实际胜出的那一路**。

另外两层：
- **状态管理**：验证过程中本来就算出了那些"紧凑的写入因子"，直接缓存起来；采样后只把被接受的那条路径取出来，而且**把状态更新推迟到下一次验证 kernel 里一起做**，省掉一次独立的状态更新步骤。
- **草稿侧**：用置信度剪枝，在验证前就砍掉低概率分支；草稿头（EAGLE 式）用目标模型的中间特征训练过，剪枝分数才准。

**效果**：H100 + 一个公开的 1.3B GDN 模型，混合测试集 **1.42×**、GSM8K **1.70×**、**HumanEval 只有 1.06×**（论文自己如实报告）。

**有没有开源代码仓**
**没有。** 实现是 PyTorch + Triton 的原型，没进任何推理框架。

**实现情况**

| 框架 | 状态 |
|---|---|
| vLLM / SGLang / vllm-ascend | 全部无。搜 "SpecLA" 在这些仓库和 issue 里都是空的 |

**查 vllm / ascend 的相关 PR 和 issue**

- 搜算法名：三个仓库都没有。
- 搜它描述的问题（"state 不能靠截断回滚"、"树的分支各需不同状态"）：对应的是 vLLM 的 RecoverSSM 系列（#61309 / #58863）、以及"变长验证"相关的 vllm-ascend [#15149](https://github.com/vllm-project/vllm-ascend/issues/15149)、[#17763](https://github.com/vllm-project/vllm-ascend/pull/17763)。
- 它的"自适应验证预算"思路，在 vllm-ascend 里已经有对应实现（[#15098](https://github.com/vllm-project/vllm-ascend/pull/15098) 已合入，[#17763](https://github.com/vllm-project/vllm-ascend/pull/17763) 正在接到 GDN 上）。

**在 Ascend 上怎么实现、有什么问题**

- **第 3 路（多链并行）最适合昇腾**：链内串行天然对应定长流水，链间并行用多核/多流；**而且不需要非因果掩码，所以能进图**。
- 第 1 路"状态留在片上"在昇腾上就是放 UB：一个 head 的状态 128×128 FP32 = 64 KB，UB 约 192 KB，**放得下**，比 GPU 的共享内存宽松。但要注意 Vector 和 Cube 之间的搬运开销。
- "把状态更新推迟到下一次验证"这招在昇腾上能省一次 kernel 启动 + 一次显存往返，值得抄。

问题：
1. **它自己的第 2 路（并行树）实测比串行还慢（16–32 节点时 0.52–1.02×）**，这条路在 Ascend 上不值得移植。
2. 它只覆盖**纯 GDN 模型**，没有 GDN + 普通注意力混合的模型，也没有 MTP，也没有分页/连续批处理。
3. 需要自己训草稿头，复现门槛高。
4. 没有代码。

# 5. DeltaLog

**论文地址**：<https://arxiv.org/abs/2608.15533>（arXiv:2608.15533，2026-08）
作者：Junqing Lin、Jingwei Sun、Guangzhong Sun（中国科学技术大学）

**解决什么问题**
它量化了一个很朴素的浪费：一个 token 真正带来的信息只有 `(d_k + d_v)` 个数，但实现上每步都要把整个 `d_k × d_v` 的状态矩阵写回显存。以 128×128 算，**写回去的量是实际信息的 64 倍**。它把这件事叫 "state-update tax"。

**实现思路**
把状态表示成"**一块稠密底 + 一份有界的近期更新日志**"：

- 平时每步只往日志里追加 `(k, u, 衰减)` 这几个小向量，**不碰稠密底**；
- 每 M 步（实测选 4 或 8）才把日志合并进稠密底一次，然后清空日志；
- 读的时候两步都要读（稠密底 + 日志），所以**它优化的是写路径，不是读路径**；
- 按输出的列切分：每块存"稠密底的这一片 + 日志的对应分片"，key 侧的数据跨块共享，每个请求-头只写一次。

**关键限制**：它只做"一次一个 token"的解码，**不覆盖投机解码的多 token 窗口**。所以它不解决"n+1 份"，它解决"每份太大/写得太频繁"。但它的日志结构本身就是一个回滚机制（挪指针）。

**效果**：写流量降 **7.83×**；内核快 **1.19–1.86×**（H200 / 4090）；端到端 **1.05–1.20×**。

**有没有开源代码仓**
**没有。** 只有论文里描述的 vLLM 原型 + 独立的 Triton kernel，没有仓库、没有 PR。

**实现情况**

| 框架 | 状态 |
|---|---|
| vLLM | 论文里是 vLLM-based 原型，**未上游** |
| SGLang | 无 |
| vllm-ascend | 无 |

**查 vllm / ascend 的相关 PR 和 issue**

- 搜 "DeltaLog"：三个仓库都没有。
- 但"减少状态写回"这件事在上游就是 RecoverSSM/ReplaySSM（同一动机）。
- 它最有价值的工程贡献是**"双 CUDA Graph"的做法**，而这个做法在昇腾上是必需的：因为"追加步"和"合并步"的语义不同，**没法用一张图表达**，所以它在预热时按批次形状捕获**两张图**（一张追加、一张合并），把"当前处于哪一步"编进图缓存的 key 里去选。这是 Ascend ACL Graph 上做同样事情的标准做法。

**在 Ascend 上怎么实现、有什么问题**

- 昇腾的显存带宽相对算力更紧，**"少写回"这件事在 Ascend 上的收益通常比在 GPU 上更大**。
- 双图范式可以直接照搬。
- 问题：
  1. 日志要能放进 UB 才划算，所以 M（合并间隔）必须按昇腾的 UB 容量重新标定，不能照抄论文的 4/8。
  2. 它对不同算子效果不一样：GDN 有效（1.05–1.11×），**KDA 几乎无感，RWKV6 甚至变慢（0.979×）**。原因和衰减结构有关。GDN 恰好是最受益的那个——这对我们算好消息。
  3. 单用无效，必须叠加一个"减份数"的方案。

# 6. DAMP

**论文地址**：<https://arxiv.org/abs/2608.27513>（arXiv:2608.27513，2026-08）
作者：Tao Zhang、Jianchao Tan、Pingwei Sun、Yanqi Yu、Zunhai Su、Zixu Jiang、Yuchen Xie、Xunliang Cai（美团）、Ziqian Zeng（华南理工）+ 华东师范

**解决什么问题**
状态默认用 FP32 存，太占内存。SGLang 上 Qwen3.6-35B、256 并发，光状态就要约 **80 GB**。想压到低精度，但一压就崩：
- INT8 / FP8：复杂推理精度掉得很厉害；
- INT4 / NVFP4：**几乎归零**（AIME 从 85.46 掉到 0.03）。

**实现思路**
先做三个观察，再设计：
1. 状态的离群值集中在**少数几个 key 通道**上；
2. 把输出维度做缩放和重排之后，量化误差仍然集中在少数 key 通道——**12.5% 的通道贡献了 69%（GDN）/ 76%（KDA）的总平方误差**；
3. 衰减慢的通道会长期保留误差，而**跨任务、跨 prompt，"哪些通道衰减慢"基本是同一批**（所以可以离线标定）。

于是：**离线**按"量化误差 × 衰减保留时间"给每个 key 通道算风险分，在固定的存储预算下，把高风险的通道存 FP16，其余存 INT8。
结果：**平均 9.9 bit/值**时平均精度接近 FP32（AIME 83.82 vs FP32 85.46），存储 **−69.1%**，状态更新 kernel 最快 **2.59×**，整模型每 token 时间最多 **−19.0%**。

**这份精度表值得单独看**（Qwen3.6-35B 的 AIME 2026，FP32 = 85.46）：

| 存法 | 每值 bit | AIME |
|---|---|---|
| FP32 | 32 | **85.46** |
| FP16 | 16 | 84.58 |
| **BF16** | 16 | **79.71（掉 5.75）** |
| FP8 | 9.0 | 29.27 |
| INT8 | 9.0 | 18.48 |
| INT8 + 缩放重排 | 9.0 | 63.98 |
| INT4 | 6.0 | 0.07 |
| NVFP4 | 4.5 | 0.03 |
| **DAMP** | **9.9** | **83.82** |

两个结论：**"换个 rounding 策略"救不回来（63.98 仍差 21 分）；连 BF16 都掉 5.75 分，别以为 BF16 就安全。**

**有没有开源代码仓**
**没有。** 论文说在 SGLang 里实现，但没有仓库、也没有任何 SGLang PR——它只是把 SGLang 当评测环境引用。

**实现情况**

| 框架 | 状态 |
|---|---|
| SGLang | 论文声称实现，无公开代码 |
| vLLM | 无 |
| vllm-ascend | 无 |

**查 vllm / ascend 的相关 PR 和 issue**

- 搜 "DAMP"：三个仓库都没有。
- 但"状态用什么精度存"这件事在 ascend 上有对应讨论：vllm-ascend [#18483](https://github.com/vllm-project/vllm-ascend/pull/18483)（记录并测试可配置的 SSM cache dtype）、[#18765](https://github.com/vllm-project/vllm-ascend/pull/18765) 的配置是"BF16 模型/卷积 + **FP32 状态**"。
- 上游相关：vLLM 那条 `use_replayssm` 的双精度 checkpoint 就是同类思想的不同实现。

**在 Ascend 上怎么实现、有什么问题**

- 昇腾的显存容量（A2 单卡 64 GB）通常是先撞墙的约束，**所以省状态内存 = 能上更多并发，收益可能比 GPU 上更大**。
- 混合精度在昇腾上的映射建议：**按 head 分成两组 kernel**（高精度的 head 一组、低精度的 head 一组），**不要在一个 kernel 里做分支**——Cube 单元最讨厌分支。
- 问题：
  1. 需要离线标定（校准集 + 每模型一套风险排序），跨模型家族能不能迁移论文没验。
  2. 9.9 bit 也不是无损（AIME 差 1.64 分）。
  3. **它不减份数**，只能当乘数用，必须叠加 ReplaySSM 那类方案。

# 7. DASC

**论文地址**：<https://arxiv.org/abs/2608.30386>（arXiv:2608.30386，v1 2026-08-31，v2 2026-10-09）
作者：华东师范 + 美团（Yanqi Yu、Pingwei Sun、Jianchao Tan、Tao Zhang、Yuchen Xie、Xunliang Cai、Yao Liu 等）

**解决什么问题**
注意：**这篇不是投机解码的工作**。它解决的是**前缀缓存（prefix cache）**的问题：混合模型为了复用一段前缀，必须把每个线性注意力层的"状态检查点"也存下来；全量存 → 内存压力大 → 缓存被频繁驱逐 → 反复重新预填充。

（它和我们的关系：投机解码的 n+1 份状态、和前缀缓存的这些检查点，**抢的是同一块显存**。TreeWY 的实验就显示"删掉快照释放的显存"能直接换成更高并发和更低首字延迟。）

**实现思路**
- 从**权重**直接算出每个 head / 通道的"信息保留时长"（不需要数据）：`H = ln(ε)/g`，g 是衰减强度的对数均值；
- 只把"保留时间长"的单元打包存进检查点（布局是不规则的 ragged）；
- 复用时，被省略的单元要么**填 0**（默认，便宜），要么**用一小段后缀重算刷新**（贵一点，精度好一点）；
- 可选在张量并行的各卡之间均衡这些检查点的存储。

**效果**：检查点压缩 **1.32–2.22×**，首字延迟 **−16.1% ~ −42.0%**，端到端 **−4.9% ~ −10.2%**。

**有一个很反直觉的发现**（在 RULER 长文检索任务上做的消融）：
- 把**普通注意力的 KV 清零** → 精度**直接归零**；
- 把**线性注意力的状态检查点清零** → 精度**只变 ≤1 分**。

说明在这些检索型任务上，承载信息的主要是普通注意力的 KV，**状态检查点不是承重的**。作者自己也很克制地加了一句："这不证明状态是冗余的"，后面更难的任务上激进压缩确实掉了 3–7 分。

**有没有开源代码仓**
**没有。**

**实现情况**

| 框架 | 状态 |
|---|---|
| SGLang | 论文声称实现，无公开代码 |
| vLLM | 无 |
| vllm-ascend | 无 |

**查 vllm / ascend 的相关 PR 和 issue**

- 搜 "DASC"：三个仓库都没有。
- 但它依赖的基础设施在 ascend 上是有讨论的：vllm-ascend **[#9508](https://github.com/vllm-project/vllm-ascend/issues/9508)**（混合前缀缓存）明确指出一个障碍：
  > "*线性注意力的 KV head 数与普通注意力不同，目前 Ascend Store 里"相同 KV head 复用状态"的逻辑不满足需求。*"
  DASC 的单元粒度是"某个 head 的某个通道"，比这个更细，所以障碍更大。
- 相关：vLLM 的 RecoverSSM 也讨论过 prefix caching（#56466），上游对"检查点"这条线也有 RFC（#52959）。

**在 Ascend 上怎么实现、有什么问题**

- **可做的部分**：默认的"填 0"策略就是一次 memset，移植成本最低；先做**静态选择 + 填 0**，只改 host 侧逻辑，不动 kernel，就能验证收益。
- **麻烦的部分**：
  1. **不规则的 ragged 布局会打断 256B/512B 对齐**，昇腾的 DMA 效率会掉，很可能把省下来的带宽又还回去。建议改成**按 head 组整体保留/丢弃**（粒度粗一点但整齐）。
  2. 跨卡的变长 all-to-all 在 HCCL 上有对应接口，但前提是"按 head 打包能在加载时排列好"，而 #9508 说明现状不满足。
  3. 它是**近似**的，作者明确说后缀刷新的结果"不是稠密前缀计算的精确复现"，难任务上掉 6–7 分。

## 最后：如果只能挑一个（也回答"在 Ascend 上选谁"）

**选 ReplaySSM 那条线**，理由不是它效果最好，而是：

1. **它已经在生产里跑了**（GLM-5.3-Flash、Kimi-K3），SGLang / TensorRT-LLM / FlashInfer 都合了；
2. **Ascend 上已经有一半**：KDA 版进了 vllm-ascend 主线，GDN 版 PR [#18765](https://github.com/vllm-project/vllm-ascend/pull/18765) 写完并测过（状态+记录 3.188 MiB vs 4 份快照 12 MiB），RFC [#19987](https://github.com/vllm-project/vllm-ascend/issues/19987) 正等人在 V2 上接着做；
3. **它只需要两种形状固定的 kernel**，能进 ACL Graph——这是昇腾上最要紧的一条；
4. 剩下三个算法**都是叠加项**：DeltaLog 减写入量、DAMP 减每份大小、DASC 减检查点。Bole 的"用矩阵乘代替解方程"是第二期做树时唯一值得抄的思路，SpecLA 的"多链并行"是第二期更省事的替代方案，TreeWY 的价值是把方程写清楚了。

**做之前先确认两件事**（都是别人踩过的坑）：
- 改验证窗口宽度时，必须**同步改 vllm-ascend 的 UB 显存核算**（[#11236](https://github.com/vllm-project/vllm-ascend/pull/11236) 的评审就因为这个问题差点 UB 溢出）。
- 算子支持图 ≠ 引擎走图。#18765 原话："*Primitive graph support does not enable an engine graph path.*"
